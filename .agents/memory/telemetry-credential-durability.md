---
name: Telemetry V2 credential durability false-confidence
description: Why telemetry V2 can report "durable (GCP)" yet fail every Secret Manager call, and how in-memory creds vanish on restart.
---

- Telemetry V2 picks its credential backend once at import. The durability check is **type-based**: it returns "durable" if the store is the GCP class, decided only from `gcp_project_id` + `GOOGLE_APPLICATION_CREDENTIALS_JSON` being present and the client initializing. It NEVER makes a live Secret Manager API call.
- Consequence: a misconfigured target project (wrong/typo'd `gcp_project_id`) or an unauthorized service account still passes the production boot guard (logs "durable (GCP)") and the in-production write/test guard, but every real store/retrieve/create then fails `403` (e.g. `CONSUMER_INVALID` on the bad project string). The fingerprint/retrieve path swallows the error and returns `{}` → sync/test surface "No credentials are stored" / "Provider call failed".
- Tell-tale: compare `settings.gcp_project_id` against the `GOOGLE_APPLICATION_CREDENTIALS_JSON` `project_id` and `client_email` domain (`<project_id>.iam.gserviceaccount.com`). A mismatch — often a subtle abbreviation typo like `ilios-prod-telemetry` vs `ilios-production-telemetry` — yields `403 CONSUMER_INVALID` on the wrong project string even though the service account is valid and in the right project. Prove it by running the Secret Manager healthcheck against the SA's OWN `project_id`: if create/add/access/delete pass there, the only fault is the configured `gcp_project_id` string.
- Related: the secret reference name (`ilios-telemetry-v2-c{company}-{hex}`) is identical between the in-memory and GCP stores. Credentials saved while on the in-memory backend (before GCP was configured, or when GCP init silently fell back) are LOST on process restart; the DB row keeps `secret_token_name` + `credential_status` but the secret never existed in GCP. Such a **dangling V2-prefixed pointer** used to make "Update Credentials" dead-end on a **404**: the PATCH update takes the rotate-in-place branch (name starts with the V2 prefix) and `add_secret_version` on a missing GCP secret is surfaced as `HTTPException(404)` by `handle_response_error`. The GCP store's `rotate()` now **self-heals** this — on a 404 it recreates the secret resource and writes the first version (tolerating a concurrent-create 409) — so the operator just clicks Update Credentials again with real creds; no account recreation needed.

**Why:** Real incident — after creds were entered and a 71-site AlsoEnergy sync succeeded within one dev process lifetime (in-memory), a restart wiped them; the GCP store then 403'd with `CONSUMER_INVALID` because the configured `gcp_project_id` was an abbreviated/typo'd string (`ilios-prod-telemetry`) that did not match the real GCP project (`ilios-production-telemetry`) — the service account itself was correct and in the right project. Once the project-id string was corrected, a live create→add→access→delete healthcheck passed. The prior `telemetry_sites_mapping` column addition (company_id/created_by_user_id) was NOT the cause — only the coincidental restart timing was.

**How to apply:** When telemetry creds "disappear" or sync fails with no-credentials / ConnectionError, FIRST diff `gcp_project_id` against the SA JSON `project_id`/`client_email` domain, then run a LIVE Secret Manager healthcheck (create→add→access→delete a throwaway secret under the `ilios-telemetry-v2-` prefix) before trusting the "durable" status or asking the user to re-enter creds. A failed sync never wipes cached `telemetry_external_sites` or `telemetry_sites_mapping` rows (verified: 71 cached sites survived a failed sync), so mappings are safe to leave in place. Production env/secret changes need a redeploy to take effect.
