# iliOS Backend Modules — Detailed Architecture

> Detailed, per-module reference for the iliOS backend (`backend/ilios-server`). This file holds the
> full feature-level prose that previously lived in `replit.md`; the top-level `replit.md` now keeps a
> concise module index and links here. Keep this file updated whenever a backend module's behavior changes.

## Technology Stack
- Python 3.11, FastAPI, SQLAlchemy, Alembic, PostgreSQL.

## Modules
- **Core Modules**: Workspace, Finance (capital governance, budgeting, vendor management), Acquisitions (13-stage deal pipeline), and Project Hub (unified asset management and due diligence).
- **Access Control**: Multi-Company Access System with granular authorization using a Canonical Effective-Access Resolver and Module-Level Permission Enforcement. Includes a Role Profiles System and a Portfolio Hub Boundary Model for data visibility.
- **Telemetry Module**: Project-scoped and company-scoped telemetry for Data Acquisition Systems (DAS) integration, health monitoring, and device mapping. Features a V2 architecture with a DB-backed provider catalog, pluggable `ProviderAdapter` abstraction, durable credential storage using GCP Secret Manager, and a three-state account model. Includes a demo telemetry system for simulated solar data.
- **Native Telemetry Ingestion (V2)**: In-platform readings ingestion that replaces the legacy GCP/BigQuery/Firestore pull. Persists raw device/site readings and interval rollups directly in PostgreSQL (no BigQuery, Firestore, or Cloud Functions; GCP Secret Manager is still used only for provider credentials). A DB-driven metric catalog (`TelemetryMetricCatalog`) maps provider fields to normalized metrics/units, and a `ReadingsAdapter` capability on the provider adapter pulls readings over a bounded window. The `run_site_refresh` ingestion service resolves the site mapping, provider account, catalog, and mapped devices, then writes via fully idempotent chunked upserts (deduped on a null-safe `dedupe_key`); it never deletes or wipes existing data, and provider/credential failures are recorded on the sync job without touching readings. A separate `run_rollups_for_window` rollup service computes epoch-anchored interval aggregates (15m/30m/1h/1d, avg) for site and device levels in an isolated transaction so a rollup failure can never undo committed readings. Every ingestion attempt is tracked as a `TelemetrySyncJob` (queued/running/succeeded/partial/failed).
- **Automatic Telemetry Scheduler**: Scheduled ingestion is handled by an in-process daemon scheduler (`TelemetrySchedulerRunner`, started from the FastAPI `lifespan`) that polls `telemetry_scheduler_state` every 60s for due sites, claims each via an atomic DB lease (so at most one run executes per site across `--reload` restarts/workers), and runs the same ingestion + bucket-aligned rollup pipeline as the manual refresh with `trigger=scheduled`. The cursor (`last_successful_pull_at`) advances only when both readings upsert and rollup succeed, so failures resume the same gap with idempotent overlap. The runner is gated behind the opt-in `telemetry_scheduler_enabled` flag AND `telemetry_v2_enabled` AND (in production-like environments) a durable credential store; when any gate fails it logs the reason at startup and never starts. Note: settings use `case_sensitive=True`, so the env var key must be lowercase (`telemetry_scheduler_enabled`).
- **Manual "Refresh Telemetry"**: User-facing manual ingestion trigger on a single mapped project/site. Backend `POST /api/telemetry/v2/sites/{site_id}/refresh-readings` (telemetry-admin + company-visibility enforced; blocked when storage is non-durable in production) accepts an optional window (defaults to the most recent 24h, clamped to a 24h max), runs the ingestion + rollup pipeline, writes a best-effort audit log, and returns a structured summary for every outcome. The frontend exposes a reusable `RefreshTelemetryButton` in the project Telemetry tab (shown once telemetry is configured) with progress, success/partial/failure feedback, and a last-refreshed indicator; on success it refreshes the site's readiness and health panels.
- **Document Versioning & Promotion**: Manages lender-quality Data Room document versions with a "Promote to Current Assumptions" workflow, supporting `candidate`, `active`, and `retired` `ProjectFact` states.
- **Due Diligence Truth-Store (V2)**: Due diligence term accept/override writes ONLY to `project_facts` (candidate → active/retired); the legacy DD→BigQuery "characteristics" write has been fully removed from the active DD flow (no BigQuery path remains in due diligence). V2 expected baselines are derived from promoted `project_facts` via the create-draft-from-facts bridge, so `SiteAdditionalFieldList` (SAFL) is no longer a V2 baseline source. The legacy SAFL-snapshot create-baseline endpoint (`POST /api/telemetry/v2/sites/{id}/expected-baselines`) is retained but **deprecated** — it still returns 201 and logs a warning steering callers to create-draft-from-facts, for manual/backfill use only. The separate device/site-card BigQuery sync is an unrelated concern and is unchanged.
- **DD Reconciliation Status Ladder (Read-Only)**: The Reconciliation screen (`GET` reconciliation endpoint → `reconciliation_service.build_site_reconciliation`) is a strictly READ-ONLY audit view that reports each canonical field's true position in the provenance chain (uploaded document → AI-extracted run value → accepted/overridden document key → candidate `project_fact` → promoted active fact → draft baseline → design points → active baseline). It replaces the old generic "Needs Review"/"Requires Value" with a precise most-advanced-stage-wins ladder: `in_active_baseline` > `in_draft_baseline` > `active_fact` > `accepted_not_promoted` (a candidate with `accepted_at`/`overridden_at`) > `candidate_only` (candidate, never accepted) > `accepted_document_value` (an accepted DocumentKey with no fact — catch-all anomaly) > `ai_extracted_only` (a completed parse-run value with no key/fact) > `superseded` (only a retired fact remains) > `missing`. Candidate selection ranks **acceptance above recency** (an older accepted candidate outranks a newer unaccepted one) so an accepted-but-unpromoted value never regresses to `candidate_only`. Each row also carries additive nullable presentation fields — `status_label`, `status_explanation`, `required_action`, a single most-severe `blocking_level` (`blocks_baseline`/`blocks_expected`/`blocks_reporting`/`lowers_confidence`/`informational`), `missing_dependencies[]`, `aliases_matched[]`, and provenance IDs (`document_id`, `document_version_id`, `ai_run_id`, `document_key_id`, `project_fact_id`, `baseline_id`, `baseline_point_id`). `needs_review` is narrowed to genuine human-resolution conflicts only: (a) an active fact with a differing candidate from another file/run, (b) no active fact but multiple distinct *accepted* candidates, or (c) a baseline-driving override with no rationale notes; equal sibling candidates are merely counted (`candidate_count`), never flagged. The `missing_required_for_baseline` warning fires ONLY when the value is truly absent everywhere; when a value exists but is unpromoted the gap is carried by `blocking_level` + `required_action`. The service performs zero writes/commits, reads baselines/points verbatim (never recomputed), never promotes, and never uses SAFL as a baseline source (SAFL stays display/comparison-only). The frontend `ReconciliationTable` renders a `StatusCell` (status chip + blocking chip + "Next: …" required-action caption + missing-dependency chips + a matched-aliases tooltip) and an "Open Data Room" deep link gated to statuses whose next step happens in the Data Room (acceptance/promotion); baseline-activation statuses show action text without a dead link.
- **Poison Pill Toggle**: Interactive flag on due diligence document keys allowing users to manually mark terms as poison pills, persisted via `is_poison_pill` and `poison_pill_notes`. User-set flags take precedence over AI-detected flags.
- **Extraction Registry & Prompt Studio**: Scalable system for dynamic document type and field configuration using database-driven schemas and prompt templates.
- **In-App AI Parsing**: Fully in-app document parsing using Replit AI Integrations (OpenAI), featuring an `InAppParsingService` for file handling, text extraction, LLM calls, observability, and retry logic. Implements idempotency and concurrency safety.
- **Storage Service Abstraction**: Replit-native storage architecture with an abstract `StorageService` interface, supporting `ReplitStorageService`, optional `GCSStorageService`, and `HybridStorageService`.
- **Data Room Acceptance Safety**: Enforces parse run history panel for files and validates `run_id` and run status before allowing bulk acceptance of extracted data.
- **Contacts System**: CRM-style contact management for tracking external people related to portfolio, company, and project entities.
- **Finance Integration & Data Ingestion**: Company-level, read-only integration supporting multiple external providers with a pluggable architecture. Encrypted credentials, role-based access, and normalized storage with upsert semantics.
- **Company & Site Creation**: Restricted company creation with structured address fields. Site creation requires `assets_management:edit` permission.
- **Per-Site Timezone**: Each Site stores an additive IANA `timezone` column (NOT NULL, server default `UTC`), set explicitly via the Site form (no auto-derivation from state). App-wide timestamps still render in the viewer's browser timezone; the site timezone is used ONLY for site-local telemetry computations — specifically the daily/"today" production boundary — by converting the site's local midnight to a naive-UTC instant for rollup queries (UTC fallback + warning on missing/invalid values, since readings/rollups are stored naive-UTC). A general `PUT /api/sites/{site_id}` endpoint (`assets_management:edit`, full-replace semantics, tolerates but ignores `company_id` so a site is never re-parented) persists site edits including the timezone.
- **Entity Directory System**: Portfolio-scoped directory of legal/business entities with project-level and deal-level role assignments, including a dedicated Portfolio Admin page and a shared `EntityPicker` UI component.
- **Project Import Tool**: Bulk import projects from CSV/XLSX files via a multi-step wizard (Upload → Map Fields → Validate → Import) with auto-mapping, validation, and duplicate detection.
- **Archive & Restore (Soft-Delete)**: Companies and Projects/Sites support soft-delete via `is_archived` flags with cascade archiving.
- **Home Dashboard "Your Projects" Widget**: Extends `/api/workspace` with project data for displaying access-controlled project cards.
- **In-App Performance Report**: Fallback reporting for demo sites where PowerBI has no BigQuery data, generating daily/monthly performance data using the demo telemetry pipeline.
- **Native Weather Provenance Foundation (W0)**: An additive, native-PostgreSQL weather domain that coexists beside the V2 telemetry stack (`telemetry_readings`/rollups are untouched and never replaced). It introduces source identity, measurement semantics, confidence, approval, and effective-period selection so weather inputs become auditable rather than implicit. Seven tables (`weather_sources`, effective-dated `weather_source_profiles`, immutable `weather_observation_batches`, append/idempotent `weather_observations`, append-only `weather_source_approvals`, `weather_device_mappings`, and a forward-placeholder `expected_weather_provenance`) plus ten named enums. **Unknown semantics stay explicit**: `irradiance_plane`, `temperature_type`, `confidence`, and `calibration_status` default to `unknown`, and W0 performs NO conversions (no GHI/DNI/DHI→POA, no ambient→cell) — unmapped DAS weather is never assumed to be POA/cell. Observations are append-only and idempotent on a unique `dedupe_key` (`INSERT … ON CONFLICT DO NOTHING`), so re-importing a window is a no-op. Source profiles are versioned by new row and never auto-activated (status defaults to `draft`); overlapping active profiles per (site, role) are intentionally allowed with a `priority` field (no single-active constraint) to leave room for a future resolver to express precedence/fallback. This is foundation-only: it adds NO external provider, secret, BigQuery, or Firestore dependency, changes no behavior in `expected_service`, telemetry ingestion, O&M charts, the scheduler, due diligence, baselines, or reconciliation, and `expected_weather_provenance` is defined but written by no runtime in W0.
- **Device Eligibility Expansion (Meters, Loggers, Gateways, Weather Devices)**: An additive expansion of telemetry device eligibility that makes meters (production/revenue), power/DAS loggers, gateways, and weather-source sensors (irradiance/temperature, reference cells) **mappable and inspectable** without letting them drive expected/O&M math. The design deliberately separates two verdicts in a single shared classifier (`device_classification.py` — `classify_device` + `is_mappable`/`drives_expected`/`is_telemetry_capable`): **mappable** is BROAD (the stable three PLUS meters/loggers/gateways/weather sensors, by category, by an operator-set `device_role`, or by an explicit capability flag) and gates only the mapping-validation and eligible-devices surfaces; **can_drive_expected** stays FROZEN to `{inverter, module, weather_station}` (category-only) and is never widened by a role or capability override. Health and readiness counts key off `drives_expected` (NOT the broad mappable set), so expanding eligibility never flips an existing site's health/readiness. A nullable-only migration (`ff33`) adds descriptive classification columns to `devices` (`device_role`, `*_capable` flags, `virtual_device`, `source_provider`, `external_device_type`, `eligibility_reason`/`ineligibility_reason`); `mapped_status` stays derived. Weather measurement **semantics are never guessed or converted** — an additive declare API on `weather_device_mappings` lets operators set `irradiance_plane`/`temperature_type`/`calibration_status` (default `unknown`), and the classifier only decides weather-source *capability*, never what readings mean (W0/WeatherResolver/import untouched). A read-only Path-B diagnostics service (`device_eligibility_diagnostics_service.py`) + endpoint (`GET /api/telemetry/v2/sites/{site_id}/eligibility-diagnostics`, asset-view + company-visibility enforced, zero writes) returns per-device and site-level eligibility/mapping/semantics indicators with `blocking_level` (`blocks_calculation`/`lowers_confidence`/`informational`) and recommended actions, surfaced in a read-only `EligibilityDiagnosticsPanel` in the project Telemetry tab. A non-destructive backfill script (`scripts/backfill_device_classification.py`) fills only NULL classification columns (idempotent, operator values never overwritten), never touches device mappings, and fingerprints every protected-site (site 4 / 110 Shawmut) telemetry-mapping ROW before/after — aborting and rolling back on any add/remove/edit, not just a count change. Role-only device types reachable solely via `device_role` (power_logger, das_logger, reference_cell, site_performance_virtual on a non-mappable category) are honored by the classifier when the column is set but have no manual role-setter API/UI yet — a deferred next-sprint item. No BigQuery/Firestore/legacy paths, no new providers or secrets, and no change to expected math, the resolver, ingestion contracts, or O&M charts.
- **Native AI Assistant (Read-Only / Propose-Only)**: A global, conversational advisor over the native Workflow Engine, entirely separate from the legacy Due-Diligence chatbot (no shared routes, services, tables, or session). The assistant may NEVER start/advance/resume/preview/execute a workflow or run, perform a governed action (promote fact, activate baseline, map/unmap device, change weather declaration), or perform any write — it runs **as the caller** (`current_user` threaded straight into the wrapped read-only services, so authorization is delegated, never bypassed). Defense-in-depth keeps the contract: tools are thin wrappers over EXISTING read-only services that never touch `db.add/commit`; `guardrails.assert_tool_allowed` runs two independent checks (name in an explicit read-only allowlist AND name not matching a prohibited-keyword screen); `dispatch_tool` is the single choke point; and the bounded tool loop rejects/records any off-catalog or mutating tool request without executing it. **Slice 2** adds: (1) **Propose-only action cards** — `action_cards.py` validates eligibility through read-only engine calls (`get_definition`/`_can_start`, `list_sequences`, owner-scoped `list_user_runs`) and emits inert deep-link cards into the EXISTING workflow UI (start `/workflows/start/{id}?site_id=&company_id=`, sequence `/workflows/sequences/{id}`, resume `/workflows/runs/{id}`); `requires_user_action` is always true and the USER clicks to perform the human-authorized handshake — the AI never starts/previews/executes. The `propose_action_card` tool name deliberately passes the prohibited-keyword screen, and `assistant_service._collect_action_cards` aggregates and dedupes cards (on kind/workflow_id/sequence_id/run_id/route) into the chat response. (2) **Isolated conversation persistence** — `conversation_store.py` over new `assistant_conversations` + `assistant_conversation_messages` tables (migration `ff41`, down_revision `ff40`), with owner-scoped CRUD: cross-user GET = 404, list is owner-only, DELETE is a soft-archive (204). The tool layer stays zero-write — only the router's persist path writes, and the legacy `chatbot_conversations` table is untouched. Router exposes `GET /config`, `POST /chat` (with a persist path that echoes `conversation_id` for thread continuity), `GET /conversations`, `GET /conversations/{id}`, and `DELETE /conversations/{id}`. (3) **Global frontend FAB + Drawer** (`src/components/assistant/*`, `src/api/assistant.ts`) mounted in `BaseLayout` inside the entity/sidebar providers; render is gated on `GET /config` success (the endpoint 404s when the flag is off, so the FAB never mounts). Advisory-only context hints (route via `useLocation`, company/site via `useEntityContext`; Project==Site so the same id is sent as both `site_id` and `project_id`) never widen authorization, the client supplies the trailing conversation `history`, and action-card "Open" buttons merely `navigate(card.route)` (the frontend performs no execution either). The entire surface is gated behind the opt-in lowercase `native_assistant_enabled` flag (settings `case_sensitive=True`, default off → `/api/assistant/*` returns 404; the auth dependency runs before the flag check, so unauthenticated callers get 401 regardless).
- **O&M / Device-Detail Drill-Down V2 Rebinding**: Rebinds the orphaned legacy O&M device-detail UI onto V2-native PostgreSQL telemetry inside existing Project Hub (PH) surfaces ONLY — no new standalone pages, no resurrection of orphaned O&M routes, and no BigQuery/Firestore/legacy-telemetry/SAFL-baseline dependencies. Expected-math, ingestion, the resolver, the classifier, and baselines are untouched, and `can_drive_expected` stays FROZEN to `{inverter, module, weather_station}`. **Backend** adds one additive, read-only optional `categories: list[DeviceCategories]` query param to `GET /api/sites/{site_id}/devices/`, threaded through `DeviceCRUD.get_site_devices` to apply `Device.category.in_(...)` BEFORE count/pagination — search, ordering, server-side pagination, and authorization are unchanged (the change is purely additive). **PH Devices grid** (AG Grid server-side paging preserved) gains FE-owned category filter groups (All / Inverters / Production meters / Weather / Gateways·DAS / Data captures) that map to the backend `categories` list, per-row eligibility/mapping/liveness chips fed by a single React-Query fetch of the site eligibility-diagnostics (built into a `Map<device_id, diagnostics>` via the shared `src/utils/telemetry/deviceDiagnostics.tsx` util, which `EligibilityDiagnosticsPanel` also consumes), and a safe CSV export that fetches ALL rows matching the current search+categories (not just the visible page) before building the file. **PH Device Details** gains (a) an Overview `DevicePerformanceCard` rendering actual-only V2 rollup bars (`device_power_ac_kw`, 1h bucket, last 24h) with honest loading/error/empty states ("No V2 telemetry readings for this device/window") and an always-on "Projected unavailable: per-device expected baseline is not defined." caption — it never renders a projected series and never fabricates 0; and (b) a PH-native Alerts tab reusing the Postgres-safe `operationsAndMaintenance.deviceAlerts` + `companyAlertResolve` APIs (the orphaned O&M route is NOT relinked), keyed off the route `deviceId`, with server-side paging and an "Unavailable" fallback for missing/invalid alert timestamps. Honest "unavailable" semantics are enforced throughout: null/'N/A'/undefined map to a neutral state, never 0%/0. Audit-only scopes confirmed `InvertersPerformance`/`ActualProduction` never render N/A as 0% and the All-Sites lifecycle grid (`SitesTable` → `GET /api/sites/`) is sourced from PostgreSQL `sites`/`site_additional_fields` (no BigQuery/legacy feed).
