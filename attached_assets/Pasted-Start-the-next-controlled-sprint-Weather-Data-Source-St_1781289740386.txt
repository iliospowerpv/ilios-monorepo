Start the next controlled sprint: Weather Data Source Strategy — Source Hierarchy, Data Availability, and V2 Integration Audit.

This is an audit/design task first. Do not implement changes yet unless a narrow bug is clearly safe.

Context:
The V2 telemetry, expected-performance, and due diligence truth-store work is now established:
- V2 actuals from PostgreSQL telemetry readings/rollups
- V2 weather-adjusted expected calculation
- V2 expected baselines from promoted project_facts
- design-estimate baseline points
- DD reconciliation visibility
- DD no longer writes to BigQuery

- SiteAdditionalFieldList is deprecated as a V2 baseline source

Objective:
Audit and design the weather data source strategy for weather-adjusted expected performance, O&M diagnostics, missing-input states, and future reporting.

Key product distinction:
- Actual production comes from V2 telemetry.
- Weather-adjusted expected uses approved baseline assumptions plus observed weather inputs.
- Design estimate comes from PVsyst/design documents.
- Weather data must be source-aware and auditable; do not silently substitute external weather without labeling it.

For each:

- metric name
- unit
- rollup behavior
- freshness
- site coverage
- gaps

2. Current expected calculation dependency
Identify exactly what expected_service requires:
- required weather inputs
- optional weather inputs
- how missing inputs are classified
- how pre-PTO is classified
- whether site-level or device-level weather is used
- whether values come from site rollups or device rollups
- how units are normalized

3. Weather source hierarchy
Propose a source hierarchy for weather-adjusted expected:
1. on-site calibrated sensor / reference cell
2. on-site weather station
3. provider DAS weather stream
4. nearby third-party weather source
5. PVsyst/design weather assumption
6. unavailable

For each level, define:
- when it is allowed
- how it should be labeled
- whether it can drive expected calculations
- whether it should produce a warning
- how it affects confidence
- whether user approval is required

- historical weather availability

- temperature availability
- licensing/cost implications
- caching/storage design
- audit/provenance requirements
