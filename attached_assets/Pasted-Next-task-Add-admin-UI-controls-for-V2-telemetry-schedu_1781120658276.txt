Context:
V2 telemetry is now working through the core operational path:
- durable company-level credentials in GCP Secret Manager
- site sync
- device sync
- site mapping
- device mapping
- manual Refresh Telemetry
- raw readings in PostgreSQL
- site/device rollups
- boundary-hour fix
- O&M actual telemetry display
- honest no-baseline UI states
- V2 inverter actual values
- V2 not-responding recency

The backend scheduler/backfill foundation already exists:
- telemetry_scheduler_state
- GET /api/telemetry/v2/sites/{site_id}/scheduler
- PUT /api/telemetry/v2/sites/{site_id}/scheduler
- GET /api/telemetry/v2/companies/{company_id}/scheduler/status
- POST /api/telemetry/v2/sites/{site_id}/backfill-readings
- cadence whitelist: PT15M, PT30M, PT1H, PT6H, PT24H
- per-site lease lock
- sync-job observability
- 30-day backfill cap
- scheduler gated off by telemetry_scheduler_enabled + telemetry_v2_enabled + durable credential store

Objective:
Expose safe admin controls in the app so admins can:
1. enable or disable automatic telemetry refresh per mapped site
2. select refresh cadence
3. view scheduler status
4. run bounded historical catch-up
5. view last run, next due, last successful pull, last error, and current lock/running state

Scope:
- Frontend/admin UI first.
- Use existing backend endpoints where possible.
- Make only narrow backend changes if the existing responses are insufficient for safe UI behavior.
- Do not change ingestion logic.
- Do not change rollup calculation.
- Do not change credentials, mappings, provider adapters, Secret Manager, BigQuery fallback, expected-baseline handling, or O&M chart logic.
- Do not add unbounded backfill.
- Do not auto-enable scheduler globally.

Placement:
Add controls in a telemetry administration/settings area where an admin managing a mapped site can find them. If there is already a Portfolio Admin / Telemetry Admin section, use that. Otherwise propose the least invasive location before coding.
