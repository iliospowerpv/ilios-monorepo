You are the Replit agent working in this repo. The Data Room versioning + Promote-to-Assumptions workflow is being implemented (Prompt #1). Now implement Prompt #2: the scalable, non-dev “Extraction Registry + Prompt Studio + Schema Versioning + Reprocess” system that eliminates hardcoding new document types/fields.

GOAL
Make it so adding a new document type, new fields, or improving prompts does NOT require code changes. The system must support:
- Document type registry
- Canonical fields registry (typed)
- Schema versions per document type (which fields to extract, required flags, ordering)
- Prompt templates per doc type (versioned, activate/deactivate, model settings)
- One-click reprocess for a document version using a selected schema/prompt version
- Evidence-ready extraction result contract (page/snippet/anchor_text at minimum; bbox optional)

HARD REQUIREMENTS (CONTRACT)
1) Registry is DB-backed from Day 1 (no more static-only ai_parsing_config.json as the authoritative source).
2) ai_parsing_config.json can be used ONLY as an initial seed import.
3) Extraction runner must build prompts dynamically from:
   - active schema version (fields)
   - active prompt template (system+extraction template)
   - document text (per-page)
4) New doc types/fields must be creatable via Admin UI and used immediately by parsing jobs.
5) Must support iterative improvement:
   - multiple prompt versions per doc type
   - activate one as current
   - reprocess older versions against newer prompts/schemas
6) Must remain compatible with the existing Data Room UX:
   - preview shows extracted fields (proposed)
   - accept/override persists DocumentKeys and candidate ProjectFacts
   - promote gate remains unchanged

SCOPE OF THIS BUILD
A) Database schema + models + CRUD
B) Admin endpoints (backend) + minimal Admin UI pages (frontend) to manage registry
C) Integrate registry into extraction pipeline (job creation, prompt building, parsing)
D) Reprocess workflow (backend + UI hook)
E) Replace any remaining “hardcoded mapping” with registry mapping

E) EXTRACTION PIPELINE INTEGRATION
Update job creation / parsing to use registry:
1) Determine document_type_id for a file version:
- Prefer: Document.name enum maps to extraction_document_types.name
- If mismatched, add a document.document_type_override_id or a mapping table; but keep minimal.
2) On parse trigger:
- load active schema version + active prompt template for the doc type
- bind job.schema_version_id and job.prompt_template_id
3) PromptBuilder:
- FIELD_LIST must be produced from canonical_fields display_name + type + required marker
Example FIELD_LIST line format:
- effective_date (date, required): Effective Date
- lessor_entity_name (text): Lessor (Landlord) Entity Name
4) ExtractionRunner:
- pass per-page text if possible; otherwise include page markers "=== Page N ==="
- enforce strict JSON output format with evidence fields (page/snippet/anchor_text; bbox optional)
5) ResultMapper:
- map output items to canonical_field_id (prefer canonical field keys rather than display strings)
- store result in AIParsingResult.result AND in job.parsed_result (whichever the current code expects)
- ensure Data Room preview continues to work

F) REPROCESS WORKFLOW
Add endpoint:
POST /api/projects/:siteId/data-room/documents/:documentId/versions/:fileId/reprocess
Body options:
{
  "schema_version_id": optional,
  "prompt_template_id": optional,
  "force": boolean default false
}
Rules:
- If schema/prompt omitted: use current active for that doc type
- Create a new document_parse_job row (do not overwrite old job row)
- Create a new AIParsingResult version record linked to fileId (or update with history; choose one and be consistent)
- The Data Room version detail view must allow selecting which extraction run to view if multiple exist (simple dropdown “Latest run” is fine)
- Reprocess does NOT auto-accept keys and does NOT auto-promote assumptions
- If force=false and a completed job exists for same bindings, return existing job id (idempotent)
