Start the next controlled sprint: Expected Performance Baseline Sprint — V2 Weather-Adjusted Expected Model.

Strategic context:
We are removing BigQuery as an operational app dependency. PostgreSQL V2 telemetry is the application source of truth for actuals. Power BI / warehouse reporting may be rebuilt later as a downstream export layer.

Important product distinction:
Do not collapse these concepts:

1. Actual

* Measured production from V2 telemetry.
* Source: AlsoEnergy native V2 readings and PostgreSQL rollups.
* Examples: site_power_ac_kw, device_power_ac_kw.

2. Design estimate / PVsyst estimate

* The modeled design expectation from diligence/design/PVsyst documents.
* Source: due diligence document upload, AI parsing, project_facts, PVsyst/design documents.
* This may be monthly/annual until an 8760 parser exists.
* This is not the live operational expected line unless it has been converted into an approved baseline model.

3. Weather-adjusted expected

* The operational expected production under actual observed field conditions.
* Source: approved baseline assumptions plus V2 actual irradiance and cell temperature.
* This is what live actual-vs-expected charts previously used through the legacy BigQuery physics model.
* This should be rebuilt natively in PostgreSQL without BigQuery.

Objective:
Rebuild the expected-performance foundation in V2 PostgreSQL so Ilios can restore:

* Actual vs Expected
* Past Performance %
* Losses
* Inverter performance color thresholds
* Company/portfolio expected rollups
  without BigQuery, Firestore, or the legacy rea-telemetry pipeline.

This sprint should be implemented in safe phases. Start with the schema/model and calculation foundation. Do not overbuild the full UI until the data model and calculation are validated.

Scope for this task:
Implement Phase P3.1 / P3.2 foundation only unless otherwise approved.

Phase P3.2 — Native weather-adjusted expected calculation

Port the legacy BigQuery expected/loss physics formula into a native Python/PostgreSQL calculation service.

Requirements:

1. Locate the exact legacy formula from backend/rea-telemetry and port it transparently.
2. Do not change the physics/math unless required for correctness.
3. Use V2 rollup inputs already available:

   * site_power_ac_kw or device_power_ac_kw for actuals
   * irradiance_wm2
   * cell_temperature_f
4. Use approved baseline/model assumptions from telemetry_expected_baselines.
5. Calculate weather-adjusted expected for the same bucket boundaries used by telemetry_site_interval_rollups.
6. Store or return expected outputs in a way that O&M charts can consume later.
7. Preserve provenance:

   * baseline_id
   * calculation_method
   * source assumptions
8. If required inputs are missing, return a clear missing-input state, not zero.
9. Do not fabricate values.
10. Do not query BigQuery.
11. Do not rely on Firestore.
12. Do not re-enable the legacy rea-telemetry pipeline.

Important:
The PVsyst/design estimate is not the same as weather-adjusted expected. PVsyst/design estimates may seed baseline assumptions, monthly estimates, or future 8760 curves, but the operational expected line should be the weather-adjusted expected calculation using actual irradiance/cell temperature where available.

Review/sign-off workflow:

* AI-parsed PVsyst/design data may create a draft or review_required baseline.
* It must not become active automatically.
* Only reviewed/approved baseline records can drive live expected calculations.
* There should be one active baseline per site for a given effective period.
* Superseded baselines must remain auditable.
