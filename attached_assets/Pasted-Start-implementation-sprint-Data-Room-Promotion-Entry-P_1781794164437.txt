Start implementation sprint: Data Room Promotion Entry Point + Promotion Context Polish.

Context:
The Reconciliation Promote + Create Task sprint is complete and merged:

* Promote and Create Task actions are reachable from the Reconciliation tab.
* Promote is gated to Diligence edit users.
* Promotion uses the existing backend diff/promote endpoints.
* Promotion is correctly shown as file-version-scoped and all-or-nothing.
* The dialog re-fetches live diff before confirming.
* Removed rows are informational.
* Success messaging states that baselines/O&M expected values are not updated automatically.
* Acceptance/override remains in Data Room.
* No backend endpoints, migrations, task schema, or Site entity changes were made.

Problem:
Promotion now works from Reconciliation, but there is still no visible promotion option in the Data Room. This interrupts the normal due diligence workflow. Users review and accept/override values in Data Room, then must leave Data Room and go to Reconciliation to promote accepted values into active project_facts/current assumptions.

Objective:
Add a promotion entry point inside the existing Data Room flow so users can complete the normal diligence sequence without leaving Data Room:
accept/override → promote accepted values from the file version → Reconciliation verifies state.

Keep the Reconciliation promote action in place as a safety catch. Do not remove or regress it.

Hard constraints:

* Do not move acceptance/override out of Data Room.
* Do not add acceptance/override to Reconciliation.
* Do not create field-level promotion.
* Do not imply that promotion is single-field.
* Do not change backend promotion semantics.
* Do not add backend endpoints unless absolutely necessary.
* Do not change database schema.
* Do not create or activate baselines.
* Do not call create-draft-from-facts.
* Do not regenerate design points.
* Do not change expected math.
* Do not change telemetry ingestion.
* Do not change WeatherResolver.
* Do not change device eligibility.
* Do not change due diligence parsing/prompts.
* Do not touch plaintext secrets.
* Do not use SAFL as a baseline source.
* Do not reintroduce BigQuery, Firestore, or legacy telemetry.
* Preserve existing Data Room and Reconciliation look and feel.

Scope B — Add Data Room promote action for eligible file versions

Add a Promote action in Data Room only when:

* the file version has accepted/overridden candidate facts ready for promotion
* the user has Diligence:edit
* document_id and file_id are available
* promotion diff endpoint returns has_changes=true, or the UI can fetch diff before showing confirmation

Suggested labels:

* “Promote accepted values”
* “Promote this version”
* “Promote to current assumptions”

Avoid:

* “Promote this field”
* “Promote value”
* any wording that implies field-level promotion

Tooltip/copy:
“Promotion applies to all accepted candidate values on this file version. You will review the full diff before confirming.”

If no candidates are promotable:

* hide or disable the action
* show clear explanation if disabled:
  “No accepted candidate values are ready to promote.”

Scope C — Reuse the existing promotion dialog

Reuse the promotion diff confirmation logic built for Reconciliation.

The Data Room promote action must:

1. Call POST /api/projects/{site_id}/assumptions/promotion/diff with { file_id }.
2. Display the full file-version diff.
3. Explicitly state:
   “This promotes every accepted candidate value on this file version, not only one field.”
4. Show added/changed/removed groups.
5. Treat removed rows as informational only:
   “Informational — this version no longer carries this field.”
6. Allow optional notes.
7. Re-fetch latest diff before final confirm or ensure the existing dialog’s stale-diff protection is reused.
8. Call POST /api/projects/{site_id}/assumptions/promote with { document_id, file_id, notes }.
9. On success, invalidate/refetch:

   * Data Room document/version state
   * Reconciliation query
   * project assumptions/facts/promotions queries if cached
10. Show success message:
    “Promoted to current assumptions. Baseline/O&M expected values are not updated automatically.”

Do not duplicate dialog logic if it can be extracted into a shared component/hook.

Suggested shared component/hook names:

* PromoteVersionDialog
* usePromotionDiff
* usePromoteVersion
* PromotionDiffTable
