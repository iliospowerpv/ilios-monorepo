Start the implementation sprint: O&M / Device-Detail Drill-Down V2 Rebinding — Reuse First.

Context:
A read-only audit was completed for legacy O&M / Asset Management drill-down recovery. The audit found that most previous functionality still exists in the repository, but some pieces are migrated, redirected, unlinked, or partially orphaned.

Critical audit findings:

* The current primary site O&M experience is the Project Hub / Asset Management site detail area.
* The standalone O&M widgets are still reused by Project Hub OM.
* The actual production gauge, past performance, actual-vs-projected chart, and inverter heatmap are alive and mostly V2-first.
* The old O&M Device Details page is orphaned because its routes are commented out.
* The active Project Hub Device Details page already has the metadata/service/technical cards from the older inverter detail screen.
* The old orphaned O&M Device Details page contains useful performance chart and alerts components that should be harvested, not directly re-linked.
* The Project Hub Devices table exists but lacks the prior category filters, CSV behavior, and richer status/diagnostic chips.
* The old unified Asset Management All Sites / Pipeline / Schedule / Input Form screen no longer exists as one screen; pieces exist across Project Hub, Acquisitions, and Overview cards.
* The construction Schedule screen has no current equivalent and is out of scope for this sprint.

Strategic objective:
Recover the useful prior-version O&M/device drill-down experience by reusing existing components and rebinding them to V2-native data. Do not rebuild O&M, do not create new standalone screens, and do not reintroduce legacy data paths.

Hard constraints:

* Do not create new standalone pages.
* Do not redesign the O&M experience.
* Do not relink the old commented-out O&M Device Details route.
* Do not reintroduce BigQuery, Firestore, or legacy telemetry.
* Do not use SiteAdditionalFieldList as a V2 baseline source.
* Do not change expected calculation math.
* Do not change telemetry ingestion.
* Do not change WeatherResolver behavior.
* Do not change historical weather import behavior.
* Do not change device eligibility classifier rules.
* Do not create/approve/activate baselines.
* Do not touch due diligence parsing/prompts.
* Do not touch plaintext secrets.
* Preserve the existing Ilios look and feel:

  * Project Hub tabs
  * MUI Cards/Paper/Chips/Alerts
  * BaseTable / AG Grid
  * SearchAndActions
  * ColumnsModal
  * existing chart styles
  * existing spacing/typography/theme
  * reconciliation StatusCell-style indicator grammar

D. Honest unavailable states

For device detail and device table values that do not yet have V2-native sources, render explicit unavailable states.

Required examples:

* per-device projected unavailable
* per-device baseline unavailable
* MTBF/MTTR unavailable
* meter present but not used for site actual
* mapped device but no telemetry
* metric catalog unsupported
* weather-capable device but semantics unknown
* gateway present but child devices unmapped

Never render null/missing values as 0.

E. Missing-dependency indicators

Use the same indicator clarity standard established in Reconciliation.

For each indicator, show:

* label
* plain-language explanation
* required next action
* blocking level:

  * blocks expected
  * blocks baseline
  * blocks reporting
  * lowers confidence
  * informational

Required indicators:

* Device exists but not mapped
* Device mapped but no usable telemetry
* Metric catalog unsupported
* Gateway present but child devices unmapped
* Meter present but not used for site actual
* Weather source device present but irradiance plane unknown
* Temperature device present but temperature type unknown
* Calibration status unknown/expired
* Projected unavailable because no per-device expected baseline exists
* Expected available but weather source unverified
* Historical weather imported but not approved

Reuse the reconciliation StatusCell-style grammar where possible:

* status chip
* blocking chip
* “Next: …” caption
* missing-dependency chips
* tooltip/help text

Do not invent a new visual language.
