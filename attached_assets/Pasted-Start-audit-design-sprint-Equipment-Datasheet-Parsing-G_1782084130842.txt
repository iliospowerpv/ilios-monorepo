Start audit/design sprint: Equipment Datasheet Parsing + Governed Baseline Field Coverage.

This is an audit/design sprint only. Do not implement production code, migrations, endpoints, parser rewrites, UI changes, data repairs, or baseline changes unless a later implementation sprint is approved.

Context:
The weather-adjusted expected baseline workflow is now functional and validated in the UI:

* V2 telemetry actuals and O&M chart integrity are validated.
* Draft weather-adjusted baselines can be created.
* Reviewer-confirmed normalization and reviewer-supplied values work.
* Draft review, approve, activate, period-effective historical selection, and invalid-baseline suppression are complete.
* Site 4 has a corrected replacement baseline lifecycle.
* Reconciliation is now a core user, testing, and development tool.

The current product gap is document intelligence.

A module/inverter specification sheet was uploaded and did not produce useful operational fields. It appears the parser used generic or contractual extraction behavior rather than equipment-specific document intelligence.

Strategic objective:
Design the source-backed equipment-document workflow so Ilios can intelligently parse module datasheets, inverter datasheets, warranties, PTO/interconnection documents, equipment schedules, and PVsyst/design reports into reviewable values that support baseline readiness, O&M comparative performance, and investor reporting.

Critical workflow rule:

AI extraction is never operational truth by itself.

The required workflow is:

Document upload
→ document classification or user-selected type
→ document-type-aware extraction
→ raw extracted value + evidence + confidence
→ parsed-document / Data Room review
→ user accepts value as-is OR overrides/corrects it in the field
→ override reason/source note/user/timestamp are logged
→ optional task creation/escalation
→ accepted or overridden candidate value
→ promotion to active project_fact
→ Reconciliation reflects current truth state
→ Baseline Readiness consumes promoted approved value
→ draft baseline / review / approval / activation

Reviewer-entered values are not inferior “manual workaround” data. They are governed, auditable reviewer overrides or reviewer-supplied assumptions and must remain visibly distinct from source-extracted values.

Hard constraints:

* Do not fabricate equipment values.
* Do not silently normalize or convert units.
* Do not auto-accept, auto-override, auto-promote, auto-create baselines, or auto-activate baselines.
* Do not mutate existing project_facts or accepted values in this audit.
* Do not change expected calculation math.
* Do not change telemetry ingestion, V2 rollups, WeatherResolver, device eligibility, or baseline lifecycle.
* Do not use SAFL as a V2 baseline source.
* Do not reintroduce BigQuery, Firestore, or legacy telemetry paths.
* Do not touch plaintext secrets.
* Preserve raw value, evidence, confidence, reviewer action, override details, task linkage, source lineage, and promotion lineage.
* Preserve stale/reparse protections already implemented.
* Do not create a separate parallel truth store.

Durable platform invariant:
Never allow accepted, promoted, baseline, or O&M state to silently survive upstream source changes. Upstream changes must create a new lineage, mark dependent state stale, require re-review, or create explicit supersession. Historical data must remain preserved and auditable.

* ambiguous units require review;

L. Parser intelligence requirements

For every specialized parser:

* explain document purpose to the model;
* list app-critical fields and why they matter;
* extract raw text first;
* extract unit separately;
* return normalized candidate only when safe;
* identify table/page/evidence;
* return confidence;
* return `not_found` explicitly;
* distinguish unclear from absent;
* never infer equipment specifications from contracts or unrelated documents;
* never hallucinate missing values;
* never make a source value active automatically.
