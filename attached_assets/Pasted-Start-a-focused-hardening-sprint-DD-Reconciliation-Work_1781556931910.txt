Start a focused hardening sprint: DD/Reconciliation Workflow Hardening — Document Review to Project Truth.

Context:
The Due Diligence V2 truth-store work is complete:

* AI parsing writes ai_parsing_results
* human review creates accepted/overridden DocumentKey records
* ProjectFactsService creates project_facts candidates
* PromotionService promotes candidates into active/current project facts
* facts→draft-baseline bridge creates draft TelemetryExpectedBaseline records
* design-estimate points producer creates monthly/annual baseline points
* Reconciliation endpoint and UI tab display the audit chain
* DD→BigQuery write has been removed
* SiteAdditionalFieldList is display-only/legacy for reconciliation

Current issue:
The Reconciliation screen is showing many/all values as “Needs Review,” “Requires Value,” or candidate-like statuses even after PVsyst values were reviewed/approved in Due Diligence. We need to verify and harden the full workflow so document review correctly translates into project facts, baseline readiness, and reconciliation status.

Objective:
Make the Reconciliation screen accurately and clearly reflect the state of each value in the chain:
uploaded document → AI extracted → accepted/overridden → project_fact candidate → promoted active fact → draft baseline → design estimate points → active baseline.

Do not change the overall architecture. This is an audit/fix/hardening sprint.

Scope:

A. Reproduce the PVsyst reconciliation issue

Using the current PVsyst review workflow:

1. Upload or use existing PVsyst document.
2. Confirm AI parse fields exist.
3. Accept or override required PVsyst fields.
4. Confirm DocumentKey records are created.
5. Confirm project_facts candidates are created.
6. Promote the relevant candidates, if the workflow requires promotion.
7. Open the Reconciliation tab.
8. Confirm whether values show as:

   * candidate_only
   * accepted_not_promoted
   * active_fact
   * in_draft_baseline
   * in_active_baseline
   * missing
   * needs_review

Document the exact current failure mode.

B. Validate status semantics

Reconciliation must distinguish these states clearly:

* missing: no AI/document/fact/baseline value exists
* ai_extracted_only: AI extracted value exists but user has not accepted/overridden
* accepted_document_value: user accepted/overrode document value, but no project_fact candidate exists
* candidate_only: project_fact candidate exists but has not been promoted
* accepted_not_promoted: document value accepted and candidate exists, but not promoted to active/current assumption
* active_fact: promoted/current project_fact exists
* in_draft_baseline: value was used in draft baseline snapshot
* in_active_baseline: value is part of active baseline used for expected calculation
* superseded: older value superseded by a later active fact/baseline
* mismatch: values disagree across document/fact/baseline/legacy
* needs_review: true ambiguity or conflict requiring user review

Do not use “Needs Review” as a generic missing/default status.

C. Clarify missing dependency indicators

Where a value is missing or blocked, return/display:

* what is missing
* why it matters
* where it normally comes from
* what action is needed
* whether it blocks calculation, review, approval, reporting, or only lowers confidence

Required examples:

* “Accepted from document but not promoted to project assumptions.”
* “Required for baseline draft: module quantity is missing.”
* “Required for weather-adjusted expected: active baseline missing.”
* “Required for design points: monthly production values missing.”
* “PVsyst value exists but canonical field does not match reconciliation catalog.”
* “Legacy value differs from active project fact.”
* “Draft baseline differs from active baseline.”
* “Source document/evidence missing.”
* “Value exists as AI extraction only; review is required.”

D. Canonical field/key alignment audit

Audit and fix mismatches between:

* PVsyst specialized schema v2 fields
* extraction canonical fields
* DueDiligenceBQKeys or legacy field keys, if still referenced for naming only
* DocumentKey.key / canonical key
* project_facts.field_name / canonical_field
* reconciliation_catalog.py
* baseline_from_facts_service.py required fields
* baseline_points_service.py monthly/annual production fields

Requirements:

* One canonical field should resolve consistently across the chain.
* Reconciliation should not miss promoted facts because of key aliasing.
* Baseline readiness should not report missing values that exist under an accepted alias.
* Keep compatibility aliases if needed, but make canonical resolution explicit and tested.

E. Promotion workflow clarity

If document acceptance does not automatically promote to active project_facts, ensure the UI/API states that clearly.

If promotion is required:

* Reconciliation should show accepted_not_promoted or candidate_only, not vague needs_review.
* The UI should tell the user what action is needed: “Promote to project assumptions.”
* Do not auto-promote baseline-driving values unless existing workflow explicitly supports it and guardrails/rationale are preserved.
