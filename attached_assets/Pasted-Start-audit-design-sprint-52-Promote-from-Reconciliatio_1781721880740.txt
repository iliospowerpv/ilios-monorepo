Start audit/design sprint: #52 — Promote from Reconciliation / Promote to Current Assumptions Workflow Audit.

This is an audit and design task only. Do not implement code, migrations, endpoints, UI changes, route changes, or data-model changes.

Context:
Users can now see reconciliation truth-state in Project Hub Overview and in the Reconciliation tab, including values that are AI-extracted, accepted, accepted-not-promoted, active facts, draft baseline inputs, and active baseline inputs.

However, there does not appear to be any obvious UI path today for a user to promote accepted information into usable current assumptions / active project_facts for expected baseline or O&M use. The Reconciliation tab is read-only and currently only routes users toward the Data Room. The Data Room may or may not expose a promotion UI. This must be verified.

Strategic objective:
Audit the existing backend and frontend to determine whether a “Promote to Current Assumptions” workflow already exists, whether it is reachable in the UI, how it works if present, and what the safest UX should be for allowing users to act from Reconciliation.

Important user decisions already made:

* Acceptance and override must remain in the Data Room.
* Reconciliation must not perform AI review, acceptance, override, or reviewer rationale capture.
* Reconciliation may only ever offer the promote step after a value has already been accepted/overridden.
* Reconciliation should support both:

  1. promote-myself, when the user is permitted and the row is eligible
  2. create an assignable task, when someone else must act
* Reconciliation must not drive a value all the way into an active expected baseline in one click.
* Baseline creation, baseline rebuild, design-point generation, and baseline activation remain separate downstream workflows.
* The backend Site entity must not be renamed or changed. “Project” is UI terminology only.

Core audit questions:

1. Does promotion functionality exist in the backend?
2. Does promotion functionality exist in the frontend?
3. Is promotion reachable from the Data Room today?
4. Is promotion reachable from Reconciliation today?
5. Is promotion file-version-scoped, candidate-scoped, or field-scoped?
6. Is it all-or-nothing for a file version?
7. What permissions are required?
8. What audit trail is written?
9. What exactly changes in project_facts?
10. What does not change, especially expected baselines and O&M expected values?
11. If no usable UI exists, what is the safest first UI design?

9. Promote confirmation / diff-preview design

Design the confirmation required before any promote action.

It must show:

* value being promoted
* source document/file version
* canonical field
* all candidate values that will become active
* all active facts that will be retired
* conflicts
* user performing the action
* timestamp
* statement that baseline is not updated automatically
* next action after promotion

Require implementation to re-fetch the latest diff immediately before executing promotion so stale Reconciliation rows cannot execute promotion without refreshed confirmation.
