Start audit/design sprint: Expected Baseline Readiness Input Resolution Audit.

This is an audit and design task first. Do not implement code, migrations, endpoints, UI changes, or data-model changes unless a follow-up implementation sprint is approved.

Context:
Approve All and Promote now work as designed. Reconciliation is proving valuable as both a user tool and a development/testing tool.

However, expected production and comparative performance still do not work because the Baseline Readiness panel shows that a draft weather-adjusted baseline is not ready, no active baseline exists, and design-estimate points are missing.

Current observed blockers include:

* Missing required physics fields:

  * module_wattage
  * inverter_wattage
  * thermal_coefficient_pct
  * power_tolerance_min_pct
  * year_1_degradation_pct
  * annual_degradation_pct
  * cec_efficiency_pct
* Non-numeric promoted active facts:

  * module_wattage active fact value “340 Wp” is not numeric
  * inverter_wattage active fact value “66 kWac” is not numeric
* Optional loss fields missing:

  * dc_loss_pct
  * ac_loss_pct
  * medium_voltage_loss_pct
  * mv_line_loss_pct
    These currently default to 0% in the calculation, but should still be surfaced honestly.
* soiling_factor missing:

  * currently defaulting to 1.0
* PTO date missing:

  * expected production is NULL before PTO by design
* No active baseline exists.
* No design-estimate baseline exists.
* Design-estimate points show 0/12 months present.

Strategic objective:
Determine exactly where each required expected-baseline input should come from, whether it already exists anywhere in the diligence/document/project_facts chain, why it is not usable today, and what the right user experience should be to resolve it.

Do not guess values.
Do not fabricate missing physics inputs.
Do not normalize values silently unless the source/units are explicit and the transformation is auditable.

Hard constraints:

* Do not create or activate baselines in this audit.
* Do not change expected calculation math.
* Do not change telemetry ingestion.
* Do not change WeatherResolver.
* Do not change device eligibility.
* Do not alter historical O&M analytics.
* Do not rewrite historical project_facts.
* Do not mutate accepted values.
* Do not auto-promote anything.
* Do not auto-normalize values without an auditable rule.
* Do not use SAFL as a V2 baseline source.
* Do not reintroduce BigQuery, Firestore, or legacy telemetry.
* Do not touch plaintext secrets.
* Preserve the distinction between:

  * raw extracted value
  * accepted value
  * promoted project_fact
  * normalized baseline input
  * draft baseline
  * active baseline
  * design-estimate baseline points
  * weather-adjusted expected
  * actual telemetry

Durable platform invariant:
Never allow accepted, promoted, baseline, or O&M state to silently survive upstream source changes. Upstream changes must create a new lineage, mark dependent state stale, require re-review, or create explicit supersession. Historical data must remain preserved and auditable.

G. Normalization UX design

Design how users should handle values like “340 Wp” and “66 kWac.”

Options to compare:

1. Normalize during parsing:

   * parser separates numeric_value and unit
   * accepted value stores both
   * project_fact has normalized_value + display_value
2. Normalize during acceptance:

   * Data Room shows extracted raw value and asks user to confirm numeric/unit
3. Normalize during promotion:

   * promotion blocks or requires normalization confirmation before active fact
4. Normalize during baseline readiness:

   * active fact remains raw, baseline readiness asks for normalized baseline input
5. No normalization; require exact numeric values from parser/reviewer

For each option:

* pros
* cons
* auditability
* user effort
* engineering risk
* impact on existing facts
* whether it preserves history

Recommend the safest practical first implementation.
