We need to audit and refactor the Ilios telemetry integration architecture. The current implementation appears partially coded and incorrectly modeled. It looks like telemetry providers were created/configured at the parent application/global level, which only works for a single tenant/customer. Ilios is multi-company/multi-customer, and each company may have its own telemetry provider license, credentials, external account, and site list.
Current Problem
On the Company page, there is a “Telemetry Providers” section showing providers such as:
•	KMC 
•	AlsoEnergy 
The UI indicates these are licensed data acquisition systems this company can use. However:
1.	The provider rows are not clickable. 
2.	Providers cannot be viewed, edited, configured, tested, disabled, or removed in any useful way. 
3.	Clicking “Add Provider” opens a modal saying all supported providers are already assigned, which suggests the system treats supported providers as global/static records rather than company-specific licensed configurations. 
4.	AlsoEnergy appears to have been configured outside the app or globally, as if there will only ever be one AlsoEnergy account/license. 
5.	This breaks the intended multi-company architecture because each customer/company may have its own telemetry provider credentials and external site inventory. 
Business Requirement
Telemetry providers should be licensed and configured at the Company level, not globally at the application level.
A Company may have zero, one, or many licensed telemetry providers. For example:
•	Company A may use AlsoEnergy with its own username/password/API access. 
•	Company B may also use AlsoEnergy, but with different credentials and a different site list. 
•	Company C may use KMC. 
•	Company D may use both AlsoEnergy and KMC. 
•	Future providers must be supported without hardcoding provider behavior into one global integration. 
Project users should only be able to create project telemetry connections using providers that are licensed/configured for that company.
Known AlsoEnergy API Context
The AlsoEnergy Swagger documentation is here:
https://api.alsoenergy.com/swagger/#/Auth/Token
Important known facts:
•	The API uses POST /Auth/token. 
•	Auth uses Content-Type: application/x-www-form-urlencoded. 
•	The returned access token is a Bearer token. 
•	If a request returns 401, the app should reauthenticate and retry. 
•	The tested credentials successfully returned a token and listed 72 sites for the REA Investments account. 
•	The token appears short-lived, roughly 15–20 minutes. 
•	/Sites returned all 72 sites. 
•	/Sites/{siteId}/Hardware returned hardware inventory. 
•	BinData may return 404 depending on whether archived data is configured for that device/site/time window, so 404 for BinData should not automatically mean auth failure.

Important design rule:
•	telemetry_provider_catalog is global/static provider definition. 
•	company_telemetry_providers is the company’s licensed/configured instance. 
•	Credentials must belong to the company provider instance, not the global provider catalog. 
•	Project telemetry connections must reference the company provider instance. 
•	Project users should not see or use providers that are not licensed/configured for their company. 
If the current schema is different, propose the least disruptive migration path.

Step 4 — AlsoEnergy Integration Requirements
Create or repair an AlsoEnergy integration service with clean responsibilities:
AlsoEnergyClient
  authenticate()
  getValidToken()
  requestWithAuthRetry()
  listSites()
  listHardware(siteId)
  fetchBinData(...)
  testConnection()
Requirements:
1.	Credentials are loaded from the encrypted company-level credential record. 
2.	Token should be cached per company telemetry provider instance, not globally. 
3.	Token cache must respect expiration. 
4.	On 401, reauthenticate and retry once. 
5.	Do not store credentials or tokens in plaintext. 
6.	Do not log full tokens or passwords. 
7.	Use form-urlencoded payload for POST /Auth/token. 
8.	Treat /Sites success as a valid connection test. 
9.	Treat BinData 404 carefully: 
o	Do not mark provider credentials invalid solely because BinData returns 404. 
o	Record it as “No archive data available/configured for this request” where appropriate. 
10.	Store discovered external sites in telemetry_external_sites. 
11.	Allow project connection mapping to one or more external sites as needed.

•	Add server-side validation. Do not rely on frontend filtering.
