Start audit/design sprint: Data Room Parse / Acceptance / Promotion Transactional Integrity.

This is an audit and design task first. Do not implement code, migrations, endpoints, or UI changes unless explicitly asked in a follow-up implementation sprint.

Context:
A recent Data Room fix correctly scoped accepted values to the viewed file version. A newly uploaded document version no longer inherits accepted values from an older version.

However, a remaining integrity issue was identified:
If a user accepts values on a file version and then reprocesses/reparses that same version, the earlier acceptance does not automatically reset or become stale. Acceptance is tracked per file version, not per parse run or extraction lineage.

This is a governance issue for Ilios because accepted values, candidate facts, promoted project_facts, baselines, expected values, and O&M analytics must remain transactionally and historically correct.

Strategic objective:
Audit and design a durable transactional integrity model for Data Room parsing, acceptance, candidate facts, promotion, baselines, and downstream O&M analytics.

Hard invariant:
If the source basis changes, downstream review/promotion state must not silently remain valid.

Source basis changes include:

* document reparse
* reprocessing
* OCR/preprocessing change
* AI extraction rerun
* extraction schema version change
* prompt version change
* canonical field mapping change
* parser/model change
* manual correction to extracted value
* accepted value change
* override value change
* document file version replacement
* candidate fact regeneration
* promotion/supersession

Hard constraints:

* Do not delete historical accepted values.
* Do not delete historical project_facts.
* Do not rewrite historical baselines.
* Do not rewrite historical O&M analytics.
* Do not make reparsed values automatically active.
* Do not auto-promote reparsed values.
* Do not auto-create or auto-activate baselines.
* Do not use SiteAdditionalFieldList as a baseline source.
* Do not reintroduce BigQuery/Firestore/legacy telemetry.
* Do not change expected calculation math.
* Do not change telemetry ingestion.
* Do not change WeatherResolver.
* Do not change device eligibility.
* Do not touch plaintext secrets.
* Preserve auditability, effective dates, supersession, and provenance.

C. Transactional integrity design

Design the correct future behavior.

Required principles:

* Parse runs should have lineage identity.
* Accepted/overridden values should be tied to a specific source basis.
* If the source basis changes, accepted state should become stale, invalidated, or superseded unless the value can be proven unchanged.
* Candidate facts should be tied to the accepted source basis.
* Promotion should promote a specific accepted/candidate lineage.
* Project facts should preserve effective history.
* Baselines should preserve effective history.
* O&M analytics should preserve the baseline/provenance used at the time.

Define terms:

* current parse run
* stale parse run
* accepted value
* stale accepted value
* candidate fact
* active fact
* superseded fact
* draft baseline
* active baseline
* superseded baseline
* historical analytics period
* source basis fingerprint

D. Source-basis fingerprint design

Propose how to detect whether a reparse materially changes the source basis.

Consider a fingerprint/hash over:

* file_id
* document_id
* file version id
* parser/schema version
* prompt version
* AI model/parser identifier
* extracted canonical field key
* normalized extracted value
* evidence page/snippet/bounding box if available
* accepted/override value
* document_key id
* parse run id

Design options:

1. strict invalidation on any new parse run
2. field-level fingerprint comparison
3. hybrid approach:

   * identical canonical value + same evidence → retain accepted state
   * changed value/evidence/schema → stale/review required
   * removed field → stale/missing review required
   * added field → new unreviewed value

Recommend the safest practical option.

E. State transition design

For each event, define expected state transitions:

Event: same file version reparsed with no material changes
Expected behavior:

* accepted values may remain valid only if fingerprint matches
* audit log records reparse and validation result

Event: same file version reparsed with changed value
Expected behavior:

* old accepted value remains historically accepted but becomes stale for current run
* new value requires review/acceptance
* candidate fact should not silently update
* promoted fact should not silently change

Event: same file version reparsed with removed field
Expected behavior:

* prior accepted value becomes stale/missing in current parse context
* Reconciliation should show source no longer present or stale source
* no automatic retirement unless explicitly promoted/superseded

Event: new file version uploaded
Expected behavior:

* new version starts unaccepted
* old version’s accepted values remain historical
* promotion can promote the chosen version only with full diff

Event: accepted value changed/overridden
Expected behavior:

* old accepted value is historical
* new accepted/override value creates a new candidate lineage
* promotion required to become active fact

Event: promoted active fact superseded
Expected behavior:

* old fact gets effective_to / superseded_by
* new active fact gets effective_from
* historical baseline/analytics remain tied to old fact for prior periods

Event: baseline rebuilt after new facts
Expected behavior:

* new draft baseline created
* old active baseline remains active until explicitly superseded/activated
* old analytics remain historical

For each status:

* label

* whether Data Room review is required

Rule:
If the accepted source basis is stale, promotion should be blocked until re-reviewed.

G. Data Room UX design

Design how Data Room should behave after reparse/preprocess changes.

Include:

* show prior accepted values as historical
* show current parse values separately
* clearly label stale accepted values
* provide re-review action
* do not silently mark stale values accepted
* accept all should operate only on the current file version and current parse run/source basis
* promote should only operate on current accepted candidate lineage
* if values changed, require explicit accept/override again
* if values are identical and fingerprint matches, optionally preserve accepted state with audit note

H. Promotion behavior design

Promotion must verify freshness before executing.

Design requirement:
Before promoting, backend should validate that candidate facts are still tied to the current accepted source basis / current parse run or a valid unchanged fingerprint.

If stale:

* block promotion
* return structured error
* user must re-review in Data Room

Promotion confirmation must show:

* file version
* parse run/source basis version
* whether accepted values are current or stale
* full diff
* downstream baseline not automatically updated

I. Baseline and O&M historical integrity

Design how active facts and baselines should respect history.

Rules:

* Promoted facts are effective-dated.
* Rebuilt baselines create new baseline versions.
* Activating a new baseline must not rewrite historical baseline outputs unless explicitly requested by a controlled backfill.
* O&M analytics before the effective date should remain tied to the then-active baseline/facts/weather inputs.
* O&M analytics after new activation should use the new active baseline.
* Any backfill/recalculation must be explicit, audited, and period-scoped.

Document whether the current system already satisfies this and where gaps exist.

J. Hard general Replit constraint

Add this as a durable platform constraint in the audit/design document and recommended future prompts:

“Never allow accepted, promoted, baseline, or O&M state to silently survive upstream source changes. Upstream changes must create a new lineage, mark dependent state stale, require re-review, or create explicit supersession. Historical data must remain preserved and auditable.”
