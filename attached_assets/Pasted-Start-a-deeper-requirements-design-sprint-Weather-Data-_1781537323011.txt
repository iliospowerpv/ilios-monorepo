Start a deeper requirements/design sprint: Weather Data Architecture — Design, Historical Backfill, Live Operations, and Reporting.

This is design only. Do not implement code or migrations.

Context:
The V2 telemetry and expected-performance foundation is now established:

* V2 actuals from PostgreSQL telemetry readings/rollups
* V2 weather-adjusted expected calculation
* V2 expected baselines from promoted project_facts
* design-estimate baseline points from PVsyst/design facts
* due diligence truth-store and reconciliation workflow
* DD no longer writes to BigQuery
* BigQuery/Firestore/legacy telemetry are not operational dependencies

Recent weather audit finding:
Today, weather-adjusted expected is driven by DAS-sourced weather inputs where available:

* irradiance_wm2
* cell_temperature_f

However, the current model does not fully distinguish:

* measured vs modeled weather
* design weather vs observed weather
* live telemetry weather vs historical reconstructed weather
* POA vs GHI/DNI/DHI irradiance
* cell/module temperature vs ambient temperature
* calibrated source vs uncalibrated source
* provider source, confidence, and approval status

We need a broader weather architecture before building W0.

Objective:
Design the full weather data architecture for Ilios across:

1. PVsyst/design weather assumptions
2. historical weather for onboarding existing sites
3. live on-site weather for operations
4. external modeled weather fallback/reconstruction
5. reporting/investor disclosure

Core product principles:

1. On-site telemetry weather should be preferred where available and reliable.
2. Historical weather is required when onboarding existing operating sites.
3. Design/PVsyst weather assumptions are not the same as observed operating weather.
4. External modeled weather must never be silently substituted.
5. Every weather value used for expected calculations must carry source, provenance, confidence, and measured/modeled status.
6. Weather source configuration must be reviewable and auditable.
7. Weather changes must not rewrite history; they must be versioned/effective by period.
8. Expected calculations must disclose which weather source was used.
9. Missing weather should remain an honest missing-input state, not a fabricated value.
10. Power BI/reporting exports later must preserve weather source metadata.
