The telemetry credential-test wiring bug has been fixed. AlsoEnergy/KMC credential testing is now internally testable, but production still uses InMemoryCredentialStore, which means credentials are lost on restart/redeploy.

We need to make telemetry credential storage durable before any broader internal use or external onboarding.

Do not implement QuickBooks.
Do not touch auth.
Do not migrate JWT storage.
Do not implement V2 Sync Sites in this sprint unless required for validation.
Do not expose credential values.
Do not print secrets.

Objective

Replace production telemetry V2 credential storage fallback behavior with durable credential storage and make production refuse unsafe in-memory credential storage.

Current confirmed state
Active telemetry credential backend: InMemoryCredentialStore
Production has gcp_project_id
Production does not have the required service-account key file mounted
_gcp_config_available() requires both service_account_key_file_path and gcp_project_id, plus the key file must exist on disk
Existing V2 credentials should be treated as non-durable and re-entered
Internal users may test credentials only with the understanding that current storage is temporary
Required Tasks
1. Inspect current credential-store selection

Document the exact code path that selects:

GCP Secret Manager credential store
In-memory credential store fallback

Identify:

required settings
required env vars
whether file-mounted credentials are mandatory
whether JSON credentials from env are supported
whether Workload Identity or Replit secrets can be supported
2. Choose safest durable production path

Implement or configure the safest production-ready option.

Preferred options, in order:

GCP Secret Manager using service account JSON from a Replit secret
Store JSON in an env var, not a committed file.
Load it safely at runtime.
Do not print the JSON.
Do not write it to repo.
If a temp file is absolutely required by the GCP library, write it to ephemeral storage with locked-down permissions and document it.
GCP Secret Manager using mounted service account key file
Only if Replit supports safe secret file mounting.
Encrypted database-backed credential store
Only if GCP Secret Manager is impractical.
Must encrypt using existing app secret strategy or a separate credential-encryption key.
Must be tenant-scoped and auditable.

Do not leave production on in-memory storage.

3. Production startup behavior

Update startup validation:

In production, if telemetry provider accounts exist or telemetry V2 is enabled, in-memory credential backend should be a hard failure.
If no provider accounts exist, either:
fail hard anyway, or
allow boot with a loud warning and block credential save/test routes.

My preference: fail hard only when telemetry V2 is enabled for production use, otherwise block credential write/test routes until durable storage is configured.

4. Block unsafe credential writes/tests

If the active backend is in-memory in production:

Block saving credentials.
Block testing credentials.
Return a clear user-facing message:
“Telemetry credential storage is not enabled for production. Contact an administrator.”
Do not accept credentials and then lose them silently.
5. Migration/cleanup behavior

Add an operator note or endpoint/process for:

identifying provider accounts whose credentials were saved under in-memory storage
marking them as requiring credential re-entry
clearing invalid fingerprints if appropriate
updating UI state to make re-entry obvious

Do not attempt to recover in-memory credentials.

6. Runbook update

Update docs/RUNBOOK.md §11 and §12 with:

durable credential backend used
exact required env vars
how to verify backend at boot
how to rotate provider credentials
how to handle credentials entered before durable storage
what internal users should do after the change
Acceptance Criteria
Production no longer silently stores telemetry V2 credentials in memory.
If durable backend is missing, credential save/test is blocked.
If durable backend is configured, credentials survive restart/redeploy.
Logs clearly identify credential backend without exposing secrets.
Existing provider accounts entered before durability are clearly treated as needing re-entry.
Runbook is updated.
No credential values are printed or committed.
