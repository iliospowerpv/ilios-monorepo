Start implementation sprint: Period-Effective Expected — Per-Segment Fail-Closed Validation.

Context:
The V2 Actual Production Curve Integrity audit is complete and architect-validated.

Confirmed findings for Site 4:

* Actual telemetry is healthy end-to-end:

  * provider raw readings vary correctly through daylight and overnight;
  * V2 normalized readings are correct;
  * V2 hourly rollups are correct;
  * the backend chart builder emits the actual series correctly.
* The apparent flat actual line is caused by the expected series.
* The default seven-day chart window spans the baseline supersede boundary.
* Historical buckets are correctly assigned period-effectively to superseded baseline #3.
* Baseline #3 is physically invalid because thermal_coefficient_pct is 350 rather than the intended approximately −0.35 %/°C.
* The period-effective expected path computes baseline #3 without applying the fail-closed baseline-physics validation used for the current active baseline.
* Invalid #3 emits extremely negative expected values, approximately −39,000 kW, which poisons the shared Y-axis and visually compresses the healthy actual curve.
* Baseline #4 is valid and active. Baseline #3 must remain immutable and superseded.

Objective:
Apply the existing read-time baseline-physics validation to every baseline segment used by period-effective expected computation.

For any historical segment whose baseline is hard-invalid:

* do not compute expected;
* return expected as null/unavailable for that segment;
* preserve actual telemetry exactly;
* expose an honest invalid-baseline-for-period state;
* ensure chart expected state becomes partial when valid and invalid segments coexist.

This is a read-only expected-path repair. It must not mutate baseline #3, baseline #4, telemetry readings, rollups, facts, documents, or historical records.

Hard constraints:

* Do not edit baseline #3.
* Do not change expected physics formula math.
* Do not add a lower bound such as max(0, expected) in this sprint.
* Do not alter raw telemetry, normalized readings, rollups, ingestion, WeatherResolver, device eligibility, or provider configuration.
* Do not run a backfill.
* Do not regenerate historical data.
* Do not alter period-effective ownership semantics.
* Do not alter active baseline lifecycle.
* Do not use BigQuery, Firestore, SAFL, or legacy telemetry as fallback.
* Preserve actual values, including genuine zero and small negative nighttime tare values.
* Preserve null expected values as null; never convert unavailable expected to zero.
* Do not hide actual telemetry when expected is invalid.

Scope A — Per-segment validation in period-effective computation

Audit and update:

* compute_site_expected_period_effective
* any helper that obtains baseline segments effective in a requested window
* expected chart builders using period-effective expected
* past-performance builders using period-effective expected

For each baseline segment:

1. run the existing physics validation policy in read-time mode;
2. if validation is non-blocking, compute expected normally;
3. if validation is blocking:

   * do not invoke expected calculation for that segment;
   * return expected null for affected buckets;
   * retain actual / irradiance values exactly as currently sourced;
   * attach additive metadata identifying:

     * baseline_id
     * baseline_validation_status = invalid
     * baseline_validation_policy_version
     * baseline_invalid_reason or validation summary
     * expected_unavailable_reason = baseline_invalid_for_period

Do not validate only the currently active baseline. Validation must apply to every period-effective baseline segment used in the requested window.

Scope B — Chart expected-state semantics

For a chart window containing:

* valid expected segments only: expected_state remains available;
* invalid baseline segments only: expected_state becomes baseline_invalid;
* both valid and invalid segments: expected_state becomes partial.

Ensure:

* the actual line remains complete and visible;
* invalid expected segments are chart gaps, not zeroes;
* valid expected segments still render;
* frontend receives enough additive metadata to explain the gap.

Scope C — O&M chart behavior

Update the actual-vs-expected and past-performance paths.

For Site 4 behavior after repair:

* the portion owned by baseline #4 should show valid expected;

* chart axis should no longer be poisoned by negative expected values;

Add a concise UI caption or tooltip for affected periods:

Scope D — Frontend defense-in-depth
